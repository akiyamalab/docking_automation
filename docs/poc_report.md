## 1. 概要

### 目的

N×M ドッキング自動化フレームワーク（docking_automation）の Phase 0 PoC として、10タンパク質 × 10化合物 = 100ペアのドッキング計算を実行し、以下の3点を検証した。

1. **基本動作確認**: AutoDock Vina Python APIを用いたN×Mドッキングの実行可能性
2. **冪等性検証**: HDF5キャッシュによる重複計算スキップ機構の動作確認
3. **段階拡張検証**: 化合物セット拡張時のインクリメンタル計算機能確認

### スコープ

- 対象タンパク質: AlphaFold DB 由来の10タンパク質（AF-P10601, AF-P10889 等）
- 対象化合物: `actives_subset.sdf`（10化合物）、拡張: `actives_extended20.sdf`（20化合物）
- 実行日: 2026-04-22

## 4. 冪等性検証結果

**結果: PASS**

- Run2 で全100ペアが HDF5 キャッシュからスキップされたことを確認
- スキップ時間: 3.5 s（Run1 の 1219.1 s の 0.29%）
- HDF5 ストア内のキー照合により、既存計算の再実行を完全に防止

## 5. 段階拡張検証結果

**結果: 条件付き PASS（論理的保証あり、直接実測なし）**

### 検証内容

`actives_extended20.sdf` に新規10化合物を追加した状態で実行した際、既存100ペアをスキップして新規100ペアのみ計算する設計を確認した。

### 限界

Run3 redo 実行時点で `actives_extended20.sdf` の新規10化合物（compound[10]〜compound[19]）の HDF5 キーが Run3_original で既に作成されていたため、直接の「新規計算実行」の実測は行えなかった。

### 根拠

HDF5 キャッシュは `(protein_id, compound_id)` の組み合わせをキーとして照合するため、新規化合物 ID が既存キーと衝突しない限り、インクリメンタル計算は設計通り動作する。

## 6. ボトルネック分析

```
Run1 実行時間の内訳（推定）:
  ドッキング計算:  12.15 s/ペア × 100 ペア = 1215 s  (99.7%)
  受容体前処理:     0.28 s/タンパク質 × 10  =    2.8 s  ( 0.2%)
  HDF5 I/O + misc:                            ≈  1.3 s  ( 0.1%)
```

**支配要因**: AutoDock Vina のドッキング計算時間（exhaustiveness=4 でも 12.15 s/ペア）

## 7. Phase 1・Phase 2 への課題・推奨事項

### Phase 1 課題

1. **ProteinSet 実装**: 複数タンパク質をまとめて管理するクラス（現在は個別ループ）
2. **GridBoxCache 実装**: タンパク質ごとのグリッドボックスを事前計算・キャッシュ
3. **AFDB 前処理パイプライン**: AlphaFold DB PDB ファイルの自動ダウンロード・前処理
4. **exhaustiveness 最適値**: PoC では 4 を使用。実用精度には 8〜32 が推奨
5. **ADFRsuite 代替の安定化**: 現在 `obabel -xr` で代替中。長期的には正式対応が望ましい

### Phase 2 課題

1. **ノード内並列化**: `cmd_002` で実装済み。本番環境での性能評価が必要
2. **分散計算**: 100,000ペア規模では単一ノードでの計算は現実的でない
3. **HDF5 並行書き込み**: 並列実行時の HDF5 競合回避策（SWMR モード等）
4. **スコアリング改善**: exhaustiveness=4 はスクリーニング精度が低い。段階的精緻化戦略を検討
